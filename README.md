
# Exleasingcar Archive

`Локальный архив публичных данных Exleasingcar.`


## Первый локальный запуск (Windows)

Сборщик запускается на локальном постоянно включённом ПК: база SQLite и
профиль Chromium остаются на диске этого ПК. GitHub Actions используется только
для Ruff/pytest CI. Автоматическое расписание пока не включено.

Из PowerShell в корне репозитория:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements-collector.txt
python -m playwright install chromium
$env:PYTHONPATH = "src"
python check_exleasingcar_keyring.py
```

Для первого глобального прохода используй отдельную долговременную БД
`data/exleasingcar_archive.sqlite3`. Не подменяй ею временные базы проверки и
не удаляй существующие данные.

1. Обнаружь все страницы списка аукционов и заполни очередь первичного сбора:

```powershell
python -m exleasingcar_archive.collector --database data/exleasingcar_archive.sqlite3 --bootstrap --discover-only --max-auctions 0
```

2. Посмотри сохранённое состояние без запуска браузера:

```powershell
python -m exleasingcar_archive.collector --database data/exleasingcar_archive.sqlite3 --plan-only
```

3. Начни пакетный первичный сбор:

```powershell
python -m exleasingcar_archive.collector --database data/exleasingcar_archive.sqlite3 --bootstrap --max-auctions 0
```

Повторяй третий шаг, пока очередь не завершится. Ограничения страниц/времени
действуют в каждом запуске; прерванные аукционы продолжаются с сохранённой
позиции. Подробная последовательность, ручная диагностика и ограничения
описаны в [operator runbook](docs/collector-operator-runbook.md).

`--rediscover-auctions` вместе с `--bootstrap` принудительно обновляет список
аукционов и добавляет новые записи в очередь, но не сбрасывает завершённые
bootstrap-задачи. Не включай автоматическое расписание, не публикуй Dashboard
в интернет и не запускай R2 операции в рамках первого прохода.


## GITHUB

### BRANCHES

- `git branch` - список локальных веток
- `git branch -r` - список веток в удаленном репозитории
- `git branch -a` - список всех локальных и удаленных веток
- `git branch -vv` - посмотреть ветки и их связь
    (Показывает:
    - Название ветки.
    - Последний коммит.
    - Связанную удаленную ветку.
    - Статус относительно удаленной ветки.)
- `git branch -d feature/my-feature` - удалить локальную ветку
    (Удаляет ветку, если она уже объединена с другой веткой.)
- `git push origin --delete feature/my-feature` - удалить удаленную ветку с GitHub

### STATUS & DIFF

- `git status` - сравнение текущих файлов с последним коммитом в текущей ветке
    (Показывает:
    - Текущую ветку.
    - Измененные файлы.
    - Новые файлы.
    - Файлы, добавленные через git add.)
- `git diff` - посмотреть разницу в коде
    (Показывает изменения, которые еще не добавлены через git add.)
- `git diff --cached` - посмотреть подготовленные изменения
    (Показывает изменения, которые уже добавлены через git add и попадут в следующий commit.)
- `git log --oneline -5` - посмотреть последние 5 коммитов
- `git log origin/master..HEAD --oneline` - посмотреть коммиты текущей ветки, которых нет в удаленном master
- `git diff origin/master...HEAD` - посмотреть изменения текущей ветки относительно общей точки, от которой она разошлась с origin/master

### REMOTE & SYNC

- `git remote -v` - посмотреть адреса удаленных репозиториев
    (Показывает:
    - Название удаленного репозитория.
    - URL для получения изменений.
    - URL для отправки изменений.)

- `git fetch origin` - обновляет локальную информацию о состоянии удаленного репозитория origin
    (fetch получает изменения и обновляет локальные ссылки на удаленные ветки согласно настройкам репозитория.
    При этом:
    - Текущая ветка не переключается.
    - Твои рабочие файлы не изменяются.
    - Локальные коммиты не объединяются с удаленными.
    - Загружаются необходимые Git-объекты и коммиты.)

- `git pull` - получает новые изменения из удаленной ветки, связанной с текущей локальной веткой, и применяет их к ней
- `git pull origin master` - получает изменения именно из удаленного master и применяет их к текущей ветке
    (Важно:
    - Команда не переключает тебя на master.
    - Изменения origin/master применяются к текущей ветке.
    - Может произойти merge или fast-forward в зависимости от ситуации и настроек Git.)

- `git config --get-all remote.origin.fetch` - проверить настройку fetch
    (Показывает, какие удаленные ветки Git получает при выполнении git fetch origin.
    Стандартная настройка:
    `+refs/heads/*:refs/remotes/origin/*`
    Означает, что Git получает информацию обо всех ветках origin.)

### CREATE & SWITCH BRANCH

- `git switch master` - переключиться на локальную ветку master
- `git switch feature/my-feature` - переключиться на существующую локальную ветку
- `git switch -c feature/my-feature` - создать новую ветку от текущей ветки и сразу переключиться на нее
- `git switch -c feature/my-feature master` - создать новую ветку от конкретной локальной ветки master и сразу переключиться на нее
- `git fetch origin` + `git switch -c feature/my-feature origin/master` - создать новую ветку от актуального удаленного master
    (1. `git fetch origin` - обновляет локальную информацию об удаленном репозитории.
    2. `git switch -c` - создает новую локальную ветку.
    3. `origin/master` - указывает, от какого коммита создавать новую ветку.
    4. Git автоматически переключает тебя на новую ветку.
    5. Переключаться отдельно на master не нужно.)

### COMMIT & PUSH

- `git add .` - добавить изменения в текущей директории и ее вложенных папках
- `git add -A` - добавить все изменения проекта
    (Добавляет:
    - Новые файлы.
    - Измененные файлы.
    - Удаленные файлы.)
- `git commit -m "feat: add new functionality"` - создать коммит
    (Сохраняет подготовленные через git add изменения в истории текущей ветки.)
- `git push -u origin feature/my-feature` - опубликовать новую локальную ветку на GitHub
    (Делает следующее:
    - Отправляет коммиты на GitHub.
    - Создает удаленную ветку, если ее еще нет.
    - Связывает локальную ветку с удаленной.)
- `git push` - отправить новые коммиты в уже связанную удаленную ветку

### PULL REQUEST & MERGE
- `git merge feature/my-feature` - объединить указанную локальную ветку с текущей локальной веткой
    (Важно:
    - Перед выполнением нужно находиться в целевой ветке.
    - Например, если ты находишься в master, команда объединит feature/my-feature в master.
    - При использовании GitHub PR выполнять эту команду локально необязательно.)

## STASH

`Stash` - временное локальное хранилище Git для незакоммиченных изменений.

### SAVE

- `git stash` - временно сохранить отслеживаемые изменения
- `git stash push -m "message"` - сохранить изменения с описанием
- `git stash push -u -m "message"` - сохранить изменения и новые файлы
    (Сохраняет:
    - Измененные отслеживаемые файлы.
    - Изменения, добавленные через git add.
    - Новые файлы, которые еще не отслеживаются Git.

    При этом:
    - Изменения убираются из рабочей директории.
    - Commit не создается.
    - Изменения не отправляются на GitHub.
    - Stash остается локально внутри Git-репозитория.)

- `git stash push -a -m "message"` - сохранить изменения, включая игнорируемые файлы
    (Параметр -a дополнительно включает файлы, указанные в .gitignore.)

### VIEW & CHECK

- `git stash list` - посмотреть все сохранения
    (Показывает:
    - Номер сохранения: stash@{0}, stash@{1} и т.д.
    - Название сохранения.
    - Ветку и коммит, на основе которых оно было создано.)

- `git stash show stash@{0}` - посмотреть список файлов в конкретном сохранении
- `git stash show -p` - посмотреть сохраненный код
- `git stash show -p 'stash@{0}'` - посмотреть полный список изменений конкретного сохранения

### APPLY & RESTORE

- `git stash apply` - вернуть последние сохраненные изменения, сохранив Stash
    (При этом:
    - Изменения возвращаются в рабочую директорию.
    - Сохранение остается в Stash.
    - Его можно применить повторно.)

- `git stash apply 'stash@{0}'` - вернуть конкретное сохранение, не удаляя его из Stash

- `git stash pop` - вернуть последние сохраненные изменения и удалить Stash при успешном применении
    (При этом:
    - Изменения возвращаются в рабочую директорию.
    - Если восстановление прошло успешно, запись удаляется из Stash.
    - Если возник конфликт, Stash остается в хранилище.)

- `git stash pop 'stash@{0}'` - вернуть конкретное сохранение и удалить его после успешного применения

- `git stash branch feature/my-feature 'stash@{0}'` - создать новую ветку и перенести в нее сохраненные изменения
    (Делает следующее:
    1. Создает ветку от коммита, на котором был создан Stash.
    2. Переключается на новую ветку.
    3. Применяет сохраненные изменения.
    4. Удаляет Stash при успешном применении.)

### DELETE

- `git stash drop` - удалить последнее сохранение
- `git stash drop 'stash@{0}'` - удалить конкретное сохранение
- `git stash clear` - удалить все сохранения из Stash
    (Важно:
    - Операция удаляет все записи Stash.
    - Не используй ее, если в Stash есть нужные изменения.)

### PRACTICAL EXAMPLES

- Сохранить изменения перед pull:
    ```bash
    git stash push -u -m "before pull"
    git pull
    git stash pop
    ```

- Перенести изменения в другую ветку:
    ```bash
    git stash push -u -m "move changes"
    git switch feature/my-feature
    git stash pop
    ```

- Посмотреть сохранения и вернуть конкретное:
    ```bash
    git stash list
    git stash apply 'stash@{0}'
    ```

- Разрешить конфликт после stash pop:
    (1. Открыть конфликтный файл.
    2. Вручную объединить нужные изменения.
    3. Удалить маркеры конфликта.
    4. Выполнить git add для разрешенного файла.
    5. Проверить результат через git status.
    6. Если Stash остался, удалить его через git stash drop только после проверки, что изменения восстановлены.)

## WORKTREE

`Worktree` - отдельная рабочая папка Git, которая использует общую Git-базу основного репозитория.

(Каждый Worktree имеет:
- Собственные файлы проекта.
- Собственную рабочую директорию.
- Собственное состояние изменений.
- Отдельную текущую ветку или коммит.

При этом:
- Все Worktrees используют общую историю коммитов.
- Все Worktrees используют общую Git-базу.
- Изменения файлов в одной папке не появляются автоматически в другой.
- Одну локальную ветку нельзя одновременно открыть в двух Worktrees.)

### VIEW & CHECK

- `git worktree list` - посмотреть все рабочие папки
    (Показывает:
    - Путь к каждой папке.
    - Текущий коммит.
    - Используемую ветку.
    - Detached HEAD, если папка открыта на конкретном коммите.)

- `git -C "Путь" status` - проверить состояние конкретной рабочей папки
    (Параметр -C позволяет выполнить команду Git в указанной папке, не переходя туда через cd.)

### CREATE WORKTREE

- `git worktree add -b feature/my-feature "C:/Users/mix123/projects/my-feature" origin/master` - создать отдельную рабочую папку и новую локальную ветку от origin/master
    (Параметры:
    - `git worktree add` - создать новую рабочую папку.
    - `-b` - создать новую локальную ветку.
    - `feature/my-feature` - название новой ветки.
    - Путь - место создания рабочей папки.
    - `origin/master` - коммит, от которого создается новая ветка.

    После выполнения:
    - Создается новая папка.
    - В ней появляется копия файлов проекта.
    - Создается новая локальная ветка.
    - Git автоматически подключает ветку к новой папке.
    - Переключаться через git switch не нужно.)

- `git worktree add "C:/Users/mix123/projects/my-feature" feature/my-feature` - создать рабочую папку для уже существующей локальной ветки
    (Ветка не должна быть открыта в другом Worktree.)

- `git worktree add --detach "C:/Users/mix123/projects/test-commit" abc123` - создать рабочую папку для конкретного коммита
    (Detached HEAD - режим, в котором Worktree привязан к конкретному коммиту, а не к ветке.
    Удобно для:
    - Проверки старой версии приложения.
    - Тестирования конкретного коммита.
    - Проверки изменений из PR.)

### REMOVE WORKTREE

- `git worktree remove "C:/Users/mix123/projects/my-feature"` - удалить рабочую папку
    (Удаляет:
    - Файлы рабочей папки.
    - Регистрацию Worktree в Git.

    При этом:
    - Сама локальная ветка не удаляется.
    - Общая Git-история не удаляется.
    - Git не позволит удалить Worktree с незакоммиченными изменениями без дополнительного подтверждения через force.)

- `git worktree prune` - удалить устаревшие записи о Worktrees, которых больше нет на диске
    (Используется, если рабочая папка была удалена вручную через Проводник Windows.)

## CHECKOUT & SWITCH

`git checkout` - старая универсальная команда Git, которая используется для переключения веток, создания веток и восстановления файлов.
(В новых командах Git ее функции разделены:
- `git switch` - работа с ветками.
- `git restore` - восстановление файлов.

`git checkout` продолжает работать, но для обычной работы с ветками и файлами удобнее использовать `switch` и `restore`.)

- `git checkout master` - переключиться на локальную ветку master
- `git checkout feature/my-feature` - переключиться на существующую локальную ветку
- `git checkout -` - вернуться на ветку, на которой ты находился до последнего переключения
- `git checkout -b feature/my-feature` - создать новую ветку от текущей ветки и сразу переключиться на нее
    (Аналог команды `git switch -c feature/my-feature`.)
- `git checkout -b feature/my-feature origin/master` - создать новую ветку от указанного коммита или ветки origin/master и переключиться на нее
- `git checkout -B feature/my-feature origin/master` - создать ветку или передвинуть уже существующую ветку на origin/master и переключиться на нее
    (Важно:
    - Если ветки еще нет, она будет создана.
    - Если ветка уже существует, ее указатель будет перемещен на origin/master.
    - Используй осторожно: можно убрать прежние коммиты ветки из ее текущей истории.)
- `git checkout --detach abc123` - перейти непосредственно на указанный коммит без переключения на ветку
    (Включает режим Detached HEAD. Новые коммиты в таком состоянии не будут принадлежать обычной ветке, пока ты не создашь ветку.)

### CHECKOUT FILES

- `git checkout -- README.md` - восстановить README.md из текущего staging area
    (Отменяет незакоммиченные изменения файла в рабочей директории, но сохраняет то, что уже было добавлено через git add.)
- `git checkout HEAD -- README.md` - восстановить README.md из последнего коммита текущей ветки
    (Обновляет файл и staging area версией из HEAD.)
- `git checkout origin/master -- README.md` - взять README.md из удаленной ветки origin/master и записать эту версию в рабочую директорию и staging area
    (Не сливает всю ветку master. Берет только указанный файл.)
- `git checkout <commit> -- README.md` - взять README.md из указанного коммита и записать эту версию в рабочую директорию и staging area
- `git checkout --ours -- README.md` - во время незавершенного merge выбрать версию README.md из текущей ветки
    (Означает ours - наша сторона, то есть ветка, в которой ты находишься и запускаешь merge.)
- `git checkout --theirs -- README.md` - во время незавершенного merge выбрать версию README.md из ветки, которую ты вливаешь в текущую
    (Означает theirs - другая сторона, то есть ветка, которую Git вливает в текущую. Например, если ты находишься в feature/privateR2 и вливаешь origin/master, то theirs - версия из origin/master.)

Важно для `git checkout`:
- `--` отделяет параметры команды от имени файла.
- `--ours` и `--theirs` применяются к файлам с конфликтами во время merge.
- После выбора `--ours` или `--theirs` нужно выполнить `git add <файл>`, чтобы отметить конфликт разрешенным.
- `git add` не отправляет файл на GitHub. Он записывает выбранное содержимое в staging area.

## RESTORE

`git restore` - современная команда для восстановления содержимого файлов. В отличие от `git switch`, она не переключает ветки.

- `git restore README.md` - отменить незакоммиченные изменения README.md в рабочей директории
    (Восстанавливает файл из staging area. Изменения, которые уже были добавлены через git add, останутся в staging area.)
- `git restore --staged README.md` - убрать README.md из staging area, не удаляя изменения из самого файла
    (Аналог команды `git reset README.md`.)
- `git restore --source=HEAD -- README.md` - восстановить README.md из последнего коммита текущей ветки
- `git restore --source=origin/master -- README.md` - взять содержимое README.md из локальной ссылки origin/master и восстановить им файл в рабочей директории
    (Важно:
    - `origin/master` должен быть предварительно обновлен через `git fetch origin`, если нужна самая свежая версия с GitHub.
    - Эта команда меняет рабочий файл, но сама по себе не отправляет изменения на GitHub.
    - Если нужно подготовить выбранную версию к коммиту, после проверки выполни `git add README.md`.)
- `git restore --source=origin/master --staged --worktree -- README.md` - восстановить README.md из origin/master одновременно в staging area и рабочей директории
    (Выбранная версия будет подготовлена к следующему коммиту.)

Важно:
- `git restore README.md` может удалить незакоммиченные изменения этого файла.
- Перед восстановлением проверь `git status` и при необходимости сохрани изменения через `git stash`.

## MERGE & CONFLICTS

- `git status` - посмотреть, есть ли незавершенный merge и какие файлы конфликтуют
- `git ls-files -u` - посмотреть записи файлов, которые находятся в состоянии конфликта
    (Во время конфликта Git может хранить для одного файла до трех версий в staging area.)
- `git show :1:README.md` - посмотреть общую исходную версию README.md до расхождения изменений
- `git show :2:README.md` - посмотреть версию README.md из текущей ветки (ours)
- `git show :3:README.md` - посмотреть версию README.md из вливаемой ветки (theirs)
    (Эти обозначения доступны для конфликтующего файла, пока конфликт не разрешен. В некоторых типах конфликтов общей версии `:1:` может не быть.)
- `git diff --ours -- README.md` - посмотреть различия рабочей версии README.md относительно версии текущей ветки при конфликте
- `git diff --theirs -- README.md` - посмотреть различия рабочей версии README.md относительно версии вливаемой ветки при конфликте
- `git checkout --ours -- README.md` - выбрать для README.md версию текущей ветки
- `git checkout --theirs -- README.md` - выбрать для README.md версию вливаемой ветки
- `git add README.md` - отметить конфликт README.md разрешенным
    (Git берет текущее содержимое файла и записывает его в staging area. Это не push и не отправка файла на GitHub.)
- `git merge --continue` - завершить текущий merge после разрешения и добавления всех конфликтующих файлов через git add
- `git commit` - также завершить текущий merge, если все конфликты разрешены и подготовлены
- `git merge --abort` - отменить незавершенный merge и попытаться вернуть рабочую директорию к состоянию до его начала
    (Используется, если ты решил не продолжать слияние. Не отменяет уже завершенный merge-коммит.)

Порядок разрешения конфликта:
1. `git status` - посмотреть конфликтующие файлы.
2. Открыть конфликтующий файл или посмотреть версии через `git show :1:`, `git show :2:` и `git show :3:`.
3. Выбрать нужную версию через `git checkout --ours` или `git checkout --theirs`, либо вручную объединить содержимое.
4. `git add <файл>` - отметить конфликт разрешенным.
5. Повторить для остальных конфликтующих файлов.
6. `git status` - убедиться, что конфликтов больше нет.
7. `git merge --continue` или `git commit` - завершить merge.

Важно:
- `ours` - текущая ветка, в которой запущен merge.
- `theirs` - ветка, которую вливают в текущую.
- `git add` после разрешения конфликта не отправляет файл на GitHub. Он сообщает Git, какую итоговую версию файла использовать.
- Если merge не нужен, используй `git merge --abort` вместо разрешения конфликтов.

## RESET & UNDO

- `git reset` - убрать все подготовленные изменения из staging area, оставив сами изменения в рабочих файлах
- `git reset README.md` - убрать README.md из staging area, не удаляя изменения из файла
    (Современная альтернатива: `git restore --staged README.md`.)
- `git reset --soft HEAD~1` - отменить последний коммит, оставив его изменения подготовленными в staging area
- `git reset --mixed HEAD~1` - отменить последний коммит и убрать его изменения из staging area, но оставить изменения в файлах
    (Это режим по умолчанию для `git reset`.)
- `git reset --hard HEAD~1` - передвинуть текущую ветку на предыдущий коммит и привести staging area и рабочие файлы к этому состоянию
    (ОПАСНО: незакоммиченные изменения будут потеряны. Используй только если точно понимаешь, что удаляешь.)
- `git revert <commit>` - отменить изменения указанного коммита с помощью нового коммита
    (В отличие от git reset, не переписывает существующую историю ветки. Обычно безопаснее для коммитов, которые уже отправлены на GitHub или доступны другим разработчикам.)

Важно:
- `git reset` меняет указатель текущей ветки и может переписывать локальную историю.
- `git reset --hard` может безвозвратно удалить незакоммиченные изменения.
- Для отмены незавершенного merge используй `git merge --abort`, а не `git reset --hard`.

## REBASE & CHERRY-PICK

- `git rebase origin/master` - перенести коммиты текущей ветки поверх актуального origin/master
    (Git последовательно переигрывает твои коммиты поверх коммитов origin/master. История текущей ветки меняется. Перед командой желательно сохранить незакоммиченные изменения.)
- `git rebase --continue` - продолжить rebase после разрешения конфликтов и добавления исправленных файлов через git add
- `git rebase --abort` - отменить незавершенный rebase и вернуть ветку к состоянию до его начала
- `git rebase --skip` - пропустить текущий коммит во время rebase
- `git cherry-pick <commit>` - применить изменения указанного коммита к текущей ветке и создать новый коммит
    (Используется, когда нужно перенести отдельный коммит из другой ветки, не объединяя всю ветку.)

## FILE OPERATIONS

- `git mv old-name new-name` - переименовать или переместить файл под контролем Git и подготовить изменение к коммиту
- `git rm README.md` - удалить отслеживаемый файл и подготовить удаление к коммиту
- `git rm --cached README.md` - убрать файл из отслеживания Git, но оставить его на диске
    (Полезно, например, если файл нужно добавить в .gitignore, но не удалять с компьютера.)
